# Implementation audit

Audit date: 2026-11-28

## Current stage

The repository is past scaffolding and has locally working core slices for a private single-shop CRM: account security, staff/RBAC, customer/consent/privacy, completed visits, WhatsApp webhook/inbox, deterministic follow-ups, templates, reviews, notifications, analytics, audit/health, and deployment configuration. It is not production-ready or feature-complete. The detailed status is in [feature traceability](feature-traceability.md).

## Repository and scope evidence

- The checkout is Git repository `oyinlola-tech/barber-crm` on `main`, synced with `origin/main` and with a clean worktree after the verified follow-up commits. The last 30 existing commits inspected contain no co-author trailers. `.env`, generated caches, local session files, test databases and browser results are ignored.
- Laravel 13.44.1, PHP 8.6, React, Inertia and TypeScript are present. The browser-push implementation adds `minishlink/web-push` 11.0.0; its required PHP cURL extension is installed in both vendor-build and runtime Docker stages.
- The local PHP 8.6 CLI has `pdo_pgsql`, but read-only `php artisan migrate:status` could not authenticate to its configured local PostgreSQL database. Its migration state and data therefore remain uninspected and unchanged.
- The active application exposes 120 routes and has 28 migration files. Booking, appointment and availability behavior is absent from the route/controller/service layer. Historical appointment/availability migration definitions remain untouched pending a safe database review.
- The owner and staff first-login credential flow and daily privacy-safe admin digest are locally implemented and tested. No production credentials, live WhatsApp delivery, provider approval, email delivery, production deployment or production backup restoration are claimed.

## Implemented and locally tested

- Private owner provisioning now generates a random 32-character temporary password, mails it over the configured private mailer, expires it after 24 hours, and requires a change before CRM access. Staff invitations send a single-use activation link and generated temporary password, store only its hash, expire both at 72 hours, and enforce the same first-login change. Argon2id password hashing, Fortify authentication, password recovery/change, email verification, TOTP MFA/recovery codes, privileged MFA enforcement, encrypted database session payloads by default, and session revocation remain in place. Successful resets rotate remembered-device tokens and revoke all database sessions; authenticated changes rotate the token and revoke other sessions. Production session cookies are forced secure. Enabling encryption invalidates pre-existing plaintext session rows, so users may need to sign in again. Credentials are never shown in CLI output; live email delivery remains unverified.
- Staff invitations, account suspension, role/permission management, delegation checks and security/audit recording. Custom roles can delegate private-note access, and built-in role slugs cannot be shadowed or renamed into.
- Custom roles can now delegate the customer-note permission, and every built-in role slug is reserved against custom role creation or rename. Regression tests cover both protections.
- Business-scoped customer CRUD, normalized international phone numbers, notes/tags, active/archived filters with profile restore, customer import/export, anonymization safeguards, consent history, opt-out processing and stated return date. Archiving cancels pending/queued follow-ups, audits the cancellation count, and restore does not reactivate those schedules; in-flight/reconciliation records remain intact. Anonymization also redacts queued raw WhatsApp message webhook payloads before delayed jobs can recreate message content. Profile updates omit protected notes for staff who can edit customer details but cannot edit notes; a mobile browser regression test covers this permission combination.
- Customer creation authorization now runs before duplicate-phone validation, so users without `customers.create` cannot use validation responses to discover whether a phone number exists. Customer import validation consistently requires both import permission and customer-list access, matching its page and post-import destination; invalid rows do not reserve duplicate numbers ahead of valid rows.
- Completed visit recording/history and after-commit visit events.
- Restoring a voided completed visit increments its automation revision and dispatches an after-commit event to schedule a fresh eligible follow-up generation; cancelled schedules remain cancelled.
- Visit corrections and restores with revision-aware follow-up replacement, audited soft-void/restore workflows, plus business-timezone input conversion and UTC persistence. Restores create a fresh follow-up generation after commit; schedules cancelled by voiding remain cancelled.
- A responsive WhatsApp connection page with reusable React feature components; typed credentials DTO, centralized typed WhatsApp configuration, numeric ID validation, phone/WABA association verification before saving, safe provider errors and audited disconnect.
- Official WhatsApp Cloud API client structure; encrypted connection settings; signed, deduplicated webhooks; inbound text/status processing; shared inbox actions and manual replies constrained by consent and the 24-hour service window.
- Delivery callbacks that arrive before the outbound message row retain a minimal provider message ID in `message_events`; a scheduled CQRS reconciliation command applies them after the outbound record appears, even if raw webhook payload retention has run. The callback-first, redacted-payload recovery path is covered by a feature regression test.
- Incoming non-text webhook messages are safely reduced to message type and timestamp; media IDs and provider payloads are not retained or downloaded. The inbox displays a generic type-specific placeholder. Processed payloads are minimized, terminal job failures redact immediately, and a configurable daily command redacts expired terminal webhook data plus stale unprocessed events, marking stalled receipts failed while preserving deduplication tombstones.
- Shared-inbox approved-template replies for the closed 24-hour service window; centralized positional variable mapping is shared with scheduled sends. The backend checks permission, consent, customer state, template approval and connection, then records provider acceptance/uncertainty; request keys and a database unique index prevent duplicate sends. Ambiguous attempts block new template sends until a new customer message; the scheduled recovery command moves stale pending attempts into reconciliation instead of retrying blindly. Focused HTTP-fake tests cover duplicate, uncertain, authorization, and stalled-dispatch outcomes; live Meta delivery is not verified.
- Manual free-form inbox replies use the same unique request-key protection: a replay of a successful request returns its existing message without another provider call, while using the key for a different body or conversation is rejected.
- Customer update audit metadata contains only changed non-note fields; private note text is excluded even when a note is changed.
- Free-form replies are persisted with unique idempotency keys, so a successful submit replay returns the existing message without a duplicate provider call; reusing a key for a different body or conversation is rejected. In-flight/pending and uncertain free-form replies are also blocked against new staff sends, and stalled-message recovery transitions crashed pending requests to uncertain and notifies authorized staff with an inbox link. Staff roster identities are sent to inbox pages only when the user can assign conversations. Uncertain-message alerts require the matching destination permission: conversations.view for inbox messages and messages.view for scheduled messages.
- Free-form inbox replies block another send while a previous text reply is pending, processing, or has uncertain delivery, until a newer inbound customer message is received; the UI displays the blocked state and backend rechecks it while locking the conversation. Automation-only viewers can inspect rules without receiving template records, and template-dependent create/edit controls remain hidden without `templates.view`.
- Newly received WhatsApp messages notify only active business members with `conversations.view`; deterministic notification IDs and same-transaction database writes prevent duplicate alerts on webhook retries. Notifications include an inbox link but no customer message content.
- Staff alerts also support email and opt-in browser push. VAPID configuration, user-owned subscription endpoints, encrypted endpoint/keys, service-worker delivery and notification actions are implemented. Web Push calls are queued after commit, endpoint hosts are constrained, requests do not follow redirects, temporary provider failures receive bounded queue retries, expired endpoints are removed, and lock-screen text excludes customer identities, dates and message content. Tests cover endpoint ownership, at-rest encryption, invalid endpoints, generic preview data and queued recipient scoping. VAPID credentials are absent in the development environment, so no live push provider delivery is claimed.
- A daily queued activity digest runs at 07:15 in the application timezone and goes to active business members with `audit.view`. It reports only per-action totals for the previous business-local day, skips empty days, and uses a daily dispatch lock, unique job, stable notification IDs, and retry-aware email delivery. It excludes actors, customer identifiers, message bodies, IP addresses, audit values, and credentials. Five focused tests cover recipient scope, empty-day behavior, privacy, template rendering, and retry idempotency. SMTP delivery remains unverified.
- Refreshed the visual system to cool slate/navy with a restrained barber-red accent, light/dark theme controls, a scissors brand mark and generated editorial barbershop art. Login and dashboard use split/illustrated hero layouts; the dashboard now uses real CRM counts and zero-safe ratios. Protected pages use a permission-aware desktop sidebar and mobile bottom navigation. A large typographic branded footer appears across the signed-in workspace and the same treatment carries into transactional email. Reference galleries guided visual structure; this is an original implementation, not a copied design.
- Removed empty `.gitkeep` scaffolding and now-empty folders, including obsolete booking and tenant-isolation placeholders. Active Laravel middleware remain in `app/Http/Middleware`; no duplicate middleware layer was introduced.
- Deterministic visit follow-up scheduling, database queue/scheduler, idempotency, sending-hours, bounded retries, stalled-message recovery, consent revalidation and delivery uncertainty handling.
- Follow-ups stop for new inbound responses and after reviews according to template purpose. Opt-out, response and review cancellation leave sending/reconciliation records intact.
- A scheduled recovery command now repairs the gap after an outbound provider send is persisted but before the next follow-up is recorded. The source and next schedule are locked and updated in one transaction with a stable idempotency key; recovery rechecks current customer status/archive, consent, rule state, latest visit, return intention and customer replies. The additive migration marks historical sent rows reconciled so old messages do not trigger new follow-ups.
- The provider-dispatch eligibility check reloads the customer and automation rule after the initial claim and consent query. Regression tests cover a return date and an archive that change during the claim window.
- The customer consent control initializes from the most recent persisted WhatsApp consent record; opt-outs remain unchecked after reloading the profile. Staff who can update customer details but cannot edit private notes can still save profile changes; the protected notes field is omitted from their request.
- Customer-note and tag CQRS commands independently check the actor's permission instead of depending only on the web Form Request. WhatsApp delivery callbacks now record `failed` after `sent`, while stale `sent`/`delivered` events cannot undo failure and stale failure events cannot regress delivered/read states.
- Customer create/update/archive/restore/anonymize/delete/import/export commands enforce business permissions themselves; note access is derived from the actor rather than a caller-controlled flag, and updates reject protected fields. Queue-failure retry backoff sanitizes invalid configuration and clears stale failure timestamps. Manual inbox replies persist a definite failure when saved WhatsApp credentials cannot be decrypted, and report sent, failed, skipped or uncertain outcomes accurately.
- Visit create, update, void and restore commands enforce their permissions when called directly, and consent recording/revocation checks the actor permission independently of its Form Request. Delayed inbound WhatsApp webhooks preserve monotonic conversation activity timestamps while retaining the delayed message and unread count. Operational WhatsApp health is degraded if the saved token cannot be decrypted, required provider IDs are missing, or the Graph API version is invalid; provider reachability and token revocation still require an external check.
- Business-profile updates now enforce `settings.update` inside the command and reject protected attributes. WhatsApp connection and disconnection commands enforce their respective permissions before provider calls or database mutation.
- Business profile now includes description, street address, an HTTPS public review link and an optional logo through an additive migration. Logo images are limited to JPEG/PNG/WebP and 2 MB, stored privately under the business ID, served through a `settings.view`-protected no-store route, and replaced/removed with transactional database updates plus old-file cleanup. Tests cover upload, replacement, removal, private route access, invalid SVG, review-link scheme validation, audit records and mobile form persistence.
- The application, queue batches, and failed-job records now default to PostgreSQL when `DB_CONNECTION` is omitted; a regression test covers these fallback settings.
- Trusted-proxy middleware rejects `*` and `**` so only explicitly configured proxies may supply forwarded IP and scheme headers.
- Custom role creation and renaming reject the reserved `owner` slug, preventing a custom role from triggering the permission resolver's protected owner shortcut.
- The roles page now receives per-role update/delete capabilities from the backend policies and limits role permission pickers to permissions the current actor may delegate. Unauthorized controls are hidden, and role deletion dependency errors are shown to staff.
- Customer anonymization now redacts internal conversation notes in the same database transaction as customer messages and other personal data.
- A failed delivery callback older than a message's recorded `sent_at` no longer downgrades its current status; the callback remains in message-event history.
- WhatsApp opt-out phrases are now owner-managed business settings with validation, normalization, persistence, audit records, and webhook enforcement; additional phrases extend the standard opt-out keywords so saving settings cannot disable `STOP` or other defaults. Staff without `settings.update` cannot change them.
- Marking a conversation as read uses an explicit internal write to the protected unread counter; a mobile browser flow now verifies assignment, internal notes, read state, close status, and consent-gated reply visibility.
- Follow-up schedules snapshot the latest inbound customer message ID. The worker rechecks that snapshot immediately before provider dispatch and cancels if a customer reply arrived during the claim window.
- Inactive-customer re-engagement rules use configured inactivity thresholds, approved retention/re-engagement templates, cycle and follow-up limits, customer consent, recent-response/frequency checks, and suppress messages while a customer-reported return date is today or later. Eligibility is checked again before delivery.
- Service catalog supports business-scoped listing, creation, editing, and reversible activation/deactivation. Mutations enforce permissions in the Form Request and CQRS command, record audit changes, and preserve inactive services out of the completed-visit service picker.
- Service categories support business-scoped listing, create/edit, ordering, assignment to services, audited deletion when unused, and prevention of deletion while assigned. Category permissions are centrally defined and migrated additively for installed manager roles.
- Staff can revoke pending invitations and update staff display names/phone numbers. The roles view includes a grouped canonical permission catalogue; authenticated HTTP tests exercise custom-role creation, permission edits, invitation role updates, guarded deletion, and audit records.
- Owner-authorized staff removal revokes active sessions and reset tokens, removes the business membership, redacts login/contact details, protects owner and self accounts, and preserves the staff profile record for existing visit/audit attribution.
- Local draft creation/editing/deletion/preview and variable mapping, provider status display, review capture/list, visit notifications, date-filtered aggregate analytics, audit log and operational health views. Draft deletion is blocked when referenced; provider templates remain manageable through enable/disable only.
- Meta template synchronization applies only a fully retrieved provider snapshot. Previously synchronized templates absent from Meta are marked locally unavailable and disabled; rejected states are disabled; templates restored or rebound to a new provider identity remain disabled until staff opt in. Provider pagination failures or repeated cursors do not alter local template state.
- When a template becomes unavailable or staff disable it, the application disables automation rules that reference it and cancels their pending or queued messages in the same transaction. In-flight sends remain subject to the normal delivery-reconciliation process.
- Operational heartbeat verification uses Laravel's database queue: health is unhealthy while the worker probe is pending, then one queue-worker iteration processes it and records the worker heartbeat.
- Docker Compose/Nginx/PHP-FPM deployment configuration, loopback default web bind, readiness route, trusted proxy configuration and deployment notes.
- Public `/ready` now returns only `ready` or `unavailable` and requires database access plus fresh scheduler and queue-worker heartbeats. The first-deploy runbook applies reviewed migrations manually before starting the web/worker/scheduler deployment, so heartbeat readiness does not require automatic or destructive schema changes.
- The database queue worker exits after one hour and Docker restarts it to release long-lived process memory. Deployment snapshots the running app and web image IDs into `previous-stable` before Compose rebuilds the `current` tags; post-start failures and `make rollback` restore that pre-deployment pair. Recovery verifies web, queue and scheduler health, and leaves database state unchanged. Fake-Docker tests verify old image IDs survive a successful deploy and are selected by rollback, plus failed deployment recovery and worker/scheduler startup failures. Production rollback remains unverified.
- Staff can review business-scoped scheduled-message history, filter by state, cancel pending/queued messages, and retry definitely failed messages up to the configured manual retry limit. Both actions enforce permissions in Form Requests and CQRS commands, are audited, and uncertain delivery cannot be retried.
- Staff with the relevant permissions can update recorded customer feedback and export business-scoped review records or safe audit columns as private CSV. Exports neutralize spreadsheet formulas and create audit entries; review edit audit metadata does not copy feedback text.
- Audit-log CSV export now uses the applied table filter instead of unsubmitted filter text; a browser test verifies the export and displayed records stay aligned.
- Account security now refreshes its session list after revocation; a browser test authenticates two independent MFA sessions, revokes one, and verifies the current session remains usable.
- Authenticated streaming encryption for PostgreSQL custom dumps, protected local artifact permissions, and a restore-to-new-database utility that refuses existing targets and leaves the active database unchanged.

## Incomplete or externally blocked

- The stated return date is stored as customer information and suppresses/cancels eligible return reminders while the date is current/future; it does not reserve a booking. No free-text WhatsApp parser infers a return date.
- Owner-managed additional opt-out phrases are implemented and locally tested; standard configured keywords remain active. Message frequency, consent language, and opt-out policy still need operational/legal review before live messaging.
- Staff removal is supported through access revocation and personal detail redaction; historical staff records remain attached to visits and audit references. Legal erasure requests may require a separate assessment of audit and regulatory retention obligations.
- Broader browser interaction, full visual QA and accessibility review remain incomplete; Playwright exercises customer creation, consent, notes, tags, visit create/correct/void/restore and representative read-only routes at 390px, but does not cover every module's write actions or a full keyboard/screen-reader audit. Targeted semantics now cover a labeled customer table and inbox unread count; broader assistive-technology testing remains outstanding.
- The configured PostgreSQL migration/schema/data review, existing-dataset constraints and any corrective migration are unverified because the local configured PostgreSQL login failed. A fresh throwaway PostgreSQL 17 database applied all 28 current migrations, including the first-login credential migration. Locking and concurrent dispatch were tested against isolated PostgreSQL 17, but production-database behavior and process restart recovery remain unverified. Historical appointment/availability migration definitions remain retained pending review of the actual database.
- Before applying the case-insensitive user email index to an existing database, check for duplicate email addresses differing only by case and resolve them through an approved account review; the migration intentionally aborts if such duplicates exist.
- A Docker image build completed successfully after adding cURL for Web Push. Deployment/rollback shell control flow passed a fake-Docker test in the prior verified revision. Production HTTPS/reverse proxy deployment, actual host rollback, restart recovery, remote encrypted backup copy, retention and production restore are unverified.
- Staff invitation, suspension, activation and role-change alerts now go to active owners and staff with audit access through database notifications and branded email, excluding the actor. Other audited changes do not all trigger email; delivery to the configured provider and broader event coverage remain external/incomplete.
- Meta credentials, business verification, webhook subscription, approved templates and live messaging; SMTP/API mail delivery; production Sentry; and legal/privacy compliance remain external setup and verification work.

The repository has no empty directories under `app`, `bootstrap`, `config`, `routes`, `resources`, `database`, or `tests`; middleware registration, trusted-proxy/security headers, single-shop resolution, privileged MFA configuration, and production-secure session cookies were audited and exercised by tests. CSP executable scripts no longer use a blanket `unsafe-inline` allowance: a fresh response nonce is applied to Vite tags and included in `script-src`.

No destructive database cleanup was performed. Before deployment, inspect the intended PostgreSQL database and migration table with an authorized backup, resolve retained historical schema safely, set production secrets, then perform controlled provider and operations verification.
